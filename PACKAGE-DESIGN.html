One package: build, test and release an agent

Design draft, 28 November 2026. Nothing here is built unless marked "Have". Statuses come from reading the repositories, not from running them. Work items: T-136 to T-138 in TODO.md.

The promise: a developer installs one thing, describes the agent, and gets a running agent with safety controls on, a simulated world to test it, checks that run in testing and in production, and a report saying whether it is safe to release.

The position: build with any framework; use ours to show the agent is safe to release. Today this is supported only by the Pydantic AI adapter.

The repositories stay separate. The package pins one tested set of versions. Resolving a profile calls a Node.js tool today; it needs a Python version or a pre-resolved file.

3. Safety controls built in

One rule decides the default. A check written in plain code may block from the first day. A check that uses a model's judgement starts in shadow (records only) and may block after it has an owner and measured evidence.

ControlWhere it actsDefaultStatus
Known prompt-injection phrasesBefore the model; after a toolBlock or hold writesPartly: a phrase list, not a classifier
Tool allowed for this user, arguments within limitsBefore a toolBlockPartly: cross-customer data check planned
Human approval for risky actionsBefore a toolBlock until decidedHave
Claims an action that never happenedReply and conversationShadowPartly: phrase version in the eval harness
Personal data in replies and tracesReply; exportRedactPartly: more Indian formats planned
Harmful contentModel input and outputCloud provider's servicePartly: needs Azure or AWS; none in the open stack
Secrets and unsafe links in outputReplyBlockGap
Cost ceiling and step limitBetween model callsBlockHave
Stop the whole agentStart of each turnSwitch, onHave
Stop a run already in progressBetween stepsOn demandGap
Forget a person's dataStored dataOn requestHave

One overlap to settle first: the agent harness has its own policy positions and the eval harness has its own hooks. Proposal: the harness is the only place that enforces in agents built on it; eval harness checks plug into those positions. The eval harness hooks remain for agents built without our harness.

4. Evaluations

WhenWhat runsResult
While buildingScripted scenarios in AgentTwin, judged by what changed in the worldFast, free, repeatable
Before releaseLive model, repeated runs for reliability, attack cases, judge checksGate verdict
While servingThe inline controls aboveBlock, redact or record
After servingDomain rules, cost rules and sampled judge checks on tracesVerdicts and a weekly report

All four write one result format. Missing evidence reads "could not judge", never "pass".

5. The assurance report

One file per release: each obligation the agent owes, the test or live check that shows it, the accepted gaps with an owner and a review date, and the versions of the specification, catalogs, model and prompts. It states that the grading is the project's own, not an outside audit.

7. Build order

This design is tested first, by walking the claims agent and the hotel agent through every step on paper. Building starts after that and after the current framework-swap step.

P1 One installPackaging, catalogs as data, command line for test and gateA clean machine runs the example with no sibling checkout and no key
P2 CreateStarter kit and suite newA new agent in a new domain reaches a gate verdict without copying the reference agent
P3 GuardDefault profiles, settled overlap, security packAn attack set runs with controls off and on, and both numbers are published
P4 Evaluate and watchOnline worker, finding to scenarioA live failure becomes a failing test, then a passing one
