Standards Adoption Plan

Read in order: At a glance → A (how the industry does it) → 0 (what you do) → 1–4 (standards and how they connect) → 5 (the plan).

How a team specifies a new agent by adopting industry standards and our open catalogs, writing only what is genuinely its own, and handing developers, testers and platform engineers generated artefacts. Draft 1, 13 Oct 2026. Owner: Basant. Delivery: after the 28 Oct grant submission.

The rule: cite, don't restate. Every standard below is adopted by reference: we point at its clauses, use its tooling, fill its templates or follow its conventions. We write only two things: what no standard says (agent-specific obligations, capabilities, the behaviour contract, the test world) and the connections between them (crosswalks and traceability). The proof: a third agent is specified this way, and we measure how much was adopted versus written.

What most of them share: (1) a lasting project layer (constitution, steering, standards); (2) per change, the trio requirements → design → tasks; (3) a person approves between steps; (4) acceptance criteria are the bridge to tests.

A.3 What the critics say, and what we take from it

A.4 The older practices underneath

  • BDD/Gherkin: examples are the tests, so the documentation stays true.
  • Pact and OpenAPI: the contract is verified in CI, and can-i-deploy blocks a release that breaks it. This is the best existing pattern for a spec that stays alive.
  • Regulated industries (DO-178C, ISO 26262, IEC 62304): requirement → design → code → test → evidence, every link two-way, rigour tiered by risk. This is the model for our chain in §4.
  • arc42 and ADRs: architecture docs kept in the repo next to the code.

A.6 So where are we?

The survey confirms the delta. Nobody covers: behavioural obligations as first-class spec items, authority limits traced back to requirements, judging by world state, operations (SLOs, cost budgets, runbooks), compliance crosswalks for agents, or an Ops role. Those are exactly the AOAS, AAC, AHC, AgentTwin and the Ops profile. Everything else (folders, workflow, requirement syntax, examples, assembly format, runtime policy engines) we adopt.

0 · If you are the Architect, BA or Ops: what you actually do

The problem today: the material is spread across five repos (AAC, AHC, AgentTwin, clean-ai-engineering, stack profiles), and nothing tells a first-liner which part concerns them. The fix: you never open the catalogs. You work in one folder per agent. The catalogs and crosswalks show up there in two forms: as questions in your template and as a to-do list from one status command.

0.1 The workflow: OpenSpec's living model, with borrowed parts

Revised after the survey (§A). Spec Kit keeps specs per branch, which is spec-first; our AOAS must stay true for the life of the agent, because the gates read it on every build. OpenSpec (MIT) is built for that: a source-of-truth folder, plus one folder per change with deltas merged back when the change is done. We adopt its structure and borrow Spec Kit's constitution and clarify markers, Kiro's EARS, BMAD's role split and SPDD's rule ("fix the spec first"). To confirm by trial: one day running OpenSpec and Spec Kit side by side on an agent #3 slice, before Phase 1 commits.

0.4 Declarative agent formats: where they fit

A family of formats now describes an agent in a file rather than in code: Oracle Open Agent Specification (framework-neutral; Python SDK PyAgentSpec, reference runtime WayFlow, adapters for LangGraph, CrewAI and AutoGen), Microsoft's declarative agents for Copilot and Agent Framework YAML, Google ADK agent config, and CrewAI's YAML. They all answer how the agent is assembled: model, prompt, tools, flow. None says what must be true of it: what it refuses, what it owes, its authority limits, how to judge it by world state. That second part is the AOAS. They are two halves, not competitors:

AOAS (ours)Oracle Open Agent Spec (adopted)
AnswersWhat must be true: purpose, refusals, operations with preconditions, authority, owed actionsHow it is assembled: agents, flows, tools, LLM config
Written byBA (approves), Arch (checks)Generated from the AOAS + harness profile; the Arch owns it
Used byThe gates, AgentTwin, the brief, the compliance reportA runtime: WayFlow, LangGraph and others
ProofThe same AgentTwin world and the same gates judge the agent whichever way it was built: our harness in Python, or a declarative runtime. This is code-to-interface at the agent level: the build route is an adapter

The third family, runtime constraints (NeMo Guardrails, AWS AgentCore Policy in Cedar, OPA): the AOAS's authority and preconditions can be generated into such a policy, so a policy engine enforces them live, while the gates still prove them in tests. Adopt where the stack has an engine; never hand-write the policy.

Recommendation: generate the Agent Spec file for all three agents (cheap, and it makes them portable), and build agent #3 both ways in Phase 4 if time allows. Whether a declarative runtime can carry approvals, budgets and owed actions as well as our harness does is itself a finding worth publishing.

4 · Connecting the dots: one chain from standard to evidence

Standard clause ─▶ AAC obligation / AHC capability ─▶ AOAS statement ─▶ test / scenario ─▶ evidence in a run
 NIST MANAGE-2.3      AAC-0057 (a person decides         issue_payout            approval scenarios     the gates' verdict
 OWASP LLM06          above a limit)                     authority + parameter   + table tests          + run records

Every link is an id, stored once. Two directions are checked:

  • Downward: a standard clause with nothing below it is either a gap to add to AAC or AHC, or declared out of scope with a reason.
  • Upward: an obligation or capability with no standard above it is our addition, and must say why.

The result is a generated compliance report per agent: for each standard, which clauses are met, by what, with which evidence, and which are gaps. A reviewer, an auditor or a customer reads that, not our code.

4b · Where each piece lives, and does code generation see it?

Rule for placement: a mapping goes in the catalog whose ids it maps. Standards about what must be true attach to AAC; standards about what must exist or how it is shaped attach to AHC; templates, profiles and tools that apply them to one agent live in clean-ai-engineering. Nothing new is a separate catalog.

So, will a new agent's generated code honour these standards? Yes, and by design it never reads them. The coding agent gets the brief, which already holds the AOAS, the AHC capabilities and the AAC obligations the agent owes. The standards arrive already translated into obligations and conventions. Two changes to tools/brief.js close the remaining gaps:

  1. Each owed obligation shows its standard clauses (e.g. "AAC-0057 · NIST MANAGE-2.3 · OWASP LLM06"), read from the crosswalks. The coder doesn't need them, but a reviewer reading the brief sees why each rule is there.
  2. A "Conventions" section is added from the stack profile, covering the things that shape code directly: OpenTelemetry version, MCP, OpenAPI, FOCUS cost columns.

The gates then prove the result, without trusting the coder: the features gate checks requirement → statement → test; the compliance report checks clause → obligation → evidence.

1 week

  • Templates, crosswalks and tools in the public repos, versioned; the agent #3 case study as the worked example
